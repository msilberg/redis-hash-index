# US-011 — the third party becomes a service

## Why

US-009 and US-010 gave the demo a read path, but the "third-party API" is still a class constructed
inside two Node processes. That hides the thing the whole write-up is about: the cache exists
because there is a **remote** system behind it, with a network hop, a latency budget and its own
failure modes. A `BillingProvider` instantiated in-process cannot time out, cannot return a 502, and
cannot be shaped like somebody else's API.

After this story the fill is three hops, each across a real boundary:

```
benchmark (seed)  --HTTP-->  test-api  --HTTP-->  mock-billing  (the "Chargebee")
                              │
                              └── @Cache(ENTITY_INDEX_CACHE) writes Redis on the miss
```

`test-api` is the only writer of cache keys, which is finally consistent with `SERVICE = "test-api"`
in the key schema.

## 1. `services/mock-billing` — the fourth service

New workspace at `services/mock-billing`, port **3003**, its own Dockerfile (node:22-alpine,
multi-stage, production deps only) and its own compose service with a healthcheck.

It owns, moved out of `packages/fixture`:

- `billing-provider.ts` → `services/mock-billing/src/provider.ts` (and its test)

It exposes exactly two routes:

```
GET /health                → { ok: true, seedValue }
GET /subscription/:userId  → 200 a Chargebee-shaped envelope
                             404 { error } when the user has no such variant
                             503 { error } when the user is FAIL_USER
```

`GET /subscription/:userId` accepts `?v=<n>` (variant, default 1) and, for realism only,
`?include_addons=true`. Validate `:userId` against `^u_\d{7}$` → 400.

### The envelope

The response is shaped like a real billing provider's, in `snake_case`, not like our internal type:

```jsonc
{
  "subscription": {
    "id": "sub_u_0000001_1",
    "customer_id": "cus_u_0000001",
    "plan_id": "pro-monthly",
    "status": "active",
    "current_term_end": 1789200000,       // unix seconds, not an ISO string
    "seats": 3,
    "object": "subscription"
  },
  "customer": { "id": "cus_u_0000001", "object": "customer" }
}
```

Every field must be **derived from the deterministic generator**, never invented per request: the
same `userId`, `SEED_VALUE` and variant must produce the same envelope on every call and in every
container. `mock-billing` imports `@redis-hash-index/fixture` for the generator; it must **not**
depend on `@redis-hash-index/cache` and must **never** open a Redis connection. Grep for both.

Environment: `PORT` (3003), `SEED_VALUE`, `ORIGIN_LATENCY_MS` (an awaited delay before answering,
default 0), `ORIGIN_FAIL_USER` (always 503). Those last two move here from `test-api`, which no
longer has an in-process origin.

## 2. `packages/fixture` keeps the generator, and only the generator

After the moves it contains `prng.ts`, `fixture.ts`, `schema.ts` and its index — the single source of
truth for what record a `(userId, variant, SEED_VALUE)` triple denotes. Both the bulk seeder and
`mock-billing` depend on it, which is exactly why it stays shared: two implementations of the
generation rules would let the bulk and lazy paths silently disagree, and every claim in the write-up
about "the same records, two ways" would be false.

Deleted from it: `billing-provider.ts` → `mock-billing`, `subscription-service.ts` → `test-api`.
`packages/fixture` must not import `@redis-hash-index/cache` afterwards.

Add one thing to it: a single **`serializeSubscription(subscription): string`** used by the bulk
seeder *and* by `test-api`'s mapper. Byte-identity between a bulk-seeded value and a lazily-filled
one depends on JSON key order, and one shared serializer is the only way to guarantee that. Two
`JSON.stringify` calls over objects built in different files is exactly the bug this prevents.

## 3. `test-api` owns the cached read

Two new files:

- `src/billing-client.ts` — the S2S client. `GET {MOCK_BILLING_URL}/subscription/:userId?v=n` with an
  `AbortController` timeout (`BILLING_TIMEOUT_MS`, default 5000). It maps the envelope to the internal
  `Subscription`, and it converts **every** non-2xx, timeout, parse failure or connection refusal into
  an `OriginError`. A 404 is the one exception: it is an authoritative "no such subscription" and
  returns `null`.
- `src/subscription-service.ts` — moved verbatim from `packages/fixture`, decorator and all:

```ts
@Cache(CacheKey.ACTIVE_SUBSCRIPTION, TTL.MEDIUM, CacheStrategy.ENTITY_INDEX_CACHE)
getActiveSubscription(userId: string, params: SubscriptionParams = {}): Promise<Subscription | null> {
  return this.billing.getActiveSubscription(userId, params);
}
```

It takes the `SubscriptionOrigin` interface as a constructor argument as it does today, so the tests
inject a stub and never open a socket.

**The `params` segment must not change.** The cache key is built by the decorator from the method's
arguments, so `GET /subscription/u_0000001?v=2` has to reach `getActiveSubscription("u_0000001", {v: 2})`
and produce a key byte-identical to the one the bulk seeder wrote for that record. Do not pass the
raw query object through — build `SubscriptionParams` explicitly, and drop anything that is not part
of the key contract. A stray `include_addons` in the params segment is a different key, a permanent
miss, and an invalidation that leaves the record behind.

Rules carried over from US-010 and still binding: an `OriginError` is never cached and the route
answers 502; a `null` (404 from the mock) is not cached either, because `cacheNegative` stays off;
`test-api` still never calls `KEYS` or `SCAN`.

## 4. The seeder fills through the chain

`services/benchmark`'s lazy paths (`SEED_MODE=lazy` and the `lazy-warm` phase) stop constructing a
`SubscriptionService` in-process. They call `test-api` over HTTP:

```
GET {TEST_API_URL}/subscription/:userId?v=<variant>     once per record, bounded by LAZY_CONCURRENCY
```

`benchmark` therefore no longer needs `configureCache` for the lazy path — only the bulk writer still
talks to Redis directly, through `registerMany`. Bulk seeding is **unchanged**: it stays pipelined and
`make up` must still write 2,000,000 records in about a minute. `ORIGIN_LATENCY_MS` and
`ORIGIN_FAIL_USER` are removed from `benchmark`'s environment; they belong to `mock-billing` now.

**Seed-value agreement, checked rather than assumed.** Three containers now share `SEED_VALUE`, and a
mismatch would produce a lazily-filled record that differs from the bulk one — a subtle, confusing
failure. Before its first lazy request the seeder reads `GET {MOCK_BILLING_URL}/health`, compares
`seedValue`, and refuses the seed with a message naming both values if they differ.

## 5. Compose and startup order

```
mock-billing  ← no dependencies
test-api      ← depends_on: redis healthy, mock-billing healthy
webhook       ← depends_on: redis healthy
benchmark     ← depends_on: redis healthy, test-api healthy, mock-billing healthy
```

`make up` waits for every healthcheck as it does today. Add `mock-billing`'s port and variables to
`.env.example` and to the README's environment table.

## 6. Remove `return await`

`return await x` is a redundant tick of the microtask queue: return the promise. Fix every site
(`packages/cache/src/strategies/default.ts`, `cache-decorator.ts`, `services/test-api/src/controller.ts`,
the moved `subscription-service.ts`, and the tests), and drop `async` from any function that then has
no `await` left in its body.

**Two exceptions, and they are not stylistic.** Keep `return await` where the call sits inside a
`try` with a `catch` or `finally` — `return somePromise()` inside a `try` escapes the block before the
promise settles, so the handler never runs. `packages/cache/src/index.test.ts:291`
(`try { return await target.smembers(key); } finally { active -= 1; }`) is exactly that case and must
stay as it is; the concurrency assertion depends on it. And when dropping `async`, check the call
site: an `async` function turns a synchronous throw into a rejected promise, while a plain function
throws synchronously. Where argument validation throws before any I/O, either keep `async` or make
sure every caller is inside a promise chain.

## Self-check

```bash
grep -rn "return await" --include=*.ts packages services   # only the try/finally in index.test.ts
grep -rn "ioredis\|redis" services/mock-billing/src        # no matches
grep -rn "@redis-hash-index/cache" packages/fixture services/mock-billing   # no matches
make typecheck && make test

make up                                   # four services healthy; 2M records in ~1 minute
curl -s localhost:3003/health | jq        # { ok: true, seedValue: 1 }
curl -s "localhost:3003/subscription/u_0000001?v=1" | jq   # snake_case envelope
curl -s "localhost:3001/subscription/u_0000001?v=1" | jq   # source:"cache" after the seed's lazy-warm

# the chain is real: stop the origin and the fill fails, the cache still serves
docker compose stop mock-billing
curl -s "localhost:3001/subscription/u_0000001?v=1" | jq -r .source          # still "cache"
curl -s -o /dev/null -w '%{http_code}\n' localhost:3001/subscription/u_0500000  # 502, nothing cached
docker compose start mock-billing

SEED_VALUE=2 docker compose up -d mock-billing && SEED_VALUE=1 make reset seed   # refuses, naming both values
make verify                                                                      # still exits 0
```

The check that actually matters, and it is not in the list above: seed one user in `bulk`, invalidate
it, refill it through the chain, and compare the stored string **byte for byte** against what the bulk
writer produced. If they differ, the mapper or the serializer is wrong and the demo's central claim —
that both paths write the same records — is false.
