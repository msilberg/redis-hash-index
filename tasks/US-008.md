# US-008 — end-to-end verification and the README

## `make verify`

One command that a stranger can run to find out whether this repo is honest. It must **exit
non-zero** on any failure — a verify script that always passes is worse than none.

```
1. docker compose up -d --build, wait for every healthcheck
2. SEED_KEYS=50000 seed, poll /api/seed/status until ready (fail after a timeout)
3. capture DBSIZE
4. start a v2 run, wait for the webhook job to reach done
5. assert: every cache key for the batch users is gone
           every index key for the batch users is gone
           an untouched control user still has its keys
           DBSIZE dropped by the expected amount
6. docker compose down -v
```

## README

Rewrite it around what a visitor needs, in this order:

1. **What this shows** — two ways to invalidate a cache, measured under load, one Redis.
2. **Quick start** — `make up`, `make seed`, open `localhost:3000`, press a button.
3. **What each run should look like** — with the committed screenshots.
4. **Costs** — 2M records ≈ 700 MB and ~1 minute to seed; 10M ≈ 3.3 GB and several minutes.
   `SEED_KEYS=10000000 make up` for the full run.
5. **Why the legacy run does not finish** — 1,000 users × one scan each is ~35 minutes at 2M and
   about 3 hours at 10M. Watch the graph for twenty seconds, press Stop.
6. **Caveats, stated plainly** — one sample per second from one client is enough to show a step
   change of four orders of magnitude, not a latency distribution. The scanned keyspace includes
   the index keys, which is a fair same-fixture comparison but not identical to a cache with no
   index. Loopback and a single Redis instance.
7. **Links** to `docs/REDIS-SCHEMA.md`, `docs/API.md`, `docs/ARCHITECTURE.md`,
   `docs/BENCHMARK-BASELINE.md`.
8. **How this was built** — the Ralph loop, `prd.json`, `tasks/`, and how to re-run it.
