# US-002 — `packages/cache`, the shared entity index

## Why this is a package and not copy-paste

`test-api` reads through the index and `webhook` invalidates through it. If those two ever build a
key differently the demo silently stops proving anything. One module, imported twice.

## Public surface

```ts
class EntityIndexCacheStrategy {
  constructor(redis: RedisClient, options: { categories: Iterable<string>; ttlSeconds?: number;
                                             batchSize?: number; concurrency?: number });
  indexKeyFor(tenant: string, category: string, entityId: string): string;
  parse(cacheKey: string): ParsedCacheKey | null;
  register(cacheKey: string, ttlSeconds: number): Promise<boolean>;
  invalidateEntities(tenant: string, category: string, entityIds: readonly string[]): Promise<InvalidationResult>;
  prune(tenant: string, category: string, entityId: string): Promise<PruneResult>;
}
```

Declare a narrow `RedisClient` interface listing only the commands used, rather than depending on
ioredis's types throughout. It keeps the module testable and it type-checks under `strict`.

## The four things that are easy to get wrong

**1. The expiry needs two commands.** `SADD` creates a persistent key, and a key with no TTL counts
as *infinite* for a `GT` comparison — so `EXPIRE ... GT` alone returns 0 forever and the index never
expires at all. Inside one `MULTI`: `SADD`, then `EXPIRE ttl NX`, then `EXPIRE ttl GT`. Then inspect
every reply tuple, because Redis does not roll back a command that fails at runtime.

**2. Order of operations in `invalidateEntities` is the design.**

```
SMEMBERS  →  UNLINK the values (batched)  →  SREM the members we observed (batched)
```

Values first. If the process dies or an `UNLINK` fails, the index still lists exactly what needs
deleting and the same call retried finishes the job. Reverse it and a failed delete has erased its
own to-do list — and a lost reply to a *successful* command is indistinguishable from a failure.

**3. `SREM` the observed members, never `DEL` the set.** A reference another writer added while you
were working was not in the list you read, and deleting the whole set would discard it silently.

**4. No timestamps anywhere.** Delete every recorded member unconditionally. Deleting an absent key
is free; skipping a live key because a client clock ran fast is a correctness bug. This is why the
index is a **set** and not a hash.

## Validation

TTL must be a whole number of seconds in `1..2592000`, checked **before** anything is written — a
rejected call must write nothing at all. Every key segment must match `[A-Za-z0-9_.-]+` so an id
containing `::` throws instead of addressing a neighbouring namespace.

## Tests that must exist

Use a real Redis (the compose one, or `redis-server --port 6399`), not a mock — three of these
only reproduce against the real command semantics.

1. First `register` sets an expiry; a longer TTL extends it; a shorter one does not pull it back.
2. A failing `UNLINK` leaves both references in place, and a retry removes everything.
3. A member added between `SMEMBERS` and `SREM` survives.
4. A rejected TTL writes nothing.
5. 200,000 members invalidate without a `RangeError` (proves batching, not spreading).

## Self-check

```bash
make typecheck && make test
```

Both exit 0, and test 2 genuinely asserts the index is intact after the injected failure.
