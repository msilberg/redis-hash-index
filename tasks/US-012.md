# US-012 — retire `/entitlement`, and mark the end of the eviction on the chart

Two unrelated finishing touches. Do them in this order: part 1 changes the endpoint the run driver
polls, and part 2 is about what that polling draws.

---

## Part 1 — `/entitlement` goes away

`GET /entitlement/:userId` was written before there was a read path. It is a second name for the same
entity, keyed by the same user id, returning a subset of what `GET /subscription/:userId` returns.
Two endpoints for one thing is one endpoint too many, and it is not how the real system worked: the
entitlement service never cached its own answer — it called the subscription service, which was the
thing with Redis in front of it.

### But read this before deleting anything

**The benchmark's run driver polls `/entitlement/:userId` once a second. That poll is the bystander
whose latency is the chart.** `scripts/verify.mjs` uses it too, for the control user. So this is not
a delete — it is a move, and the thing being moved has one property that must survive:

> The probe reads the cache and **never fills it**.

If the probe were to fill, the demo would break in two ways that are easy to miss. During a v1 run
the probe would refill users the webhook is busy evicting, so `removed`, `DBSIZE` and the whole
comparison would drift. And `make verify` asserts that a batch user's keys are *gone* after an
eviction — a filling probe recreates them, and the assertion fails or, worse, quietly passes for the
wrong reason.

### What to do

1. **Delete** the route, the controller handler, the tests written against it, and the section in
   `docs/API.md`. Keep the internal read (`SMEMBERS` + `MGET` + `hrtime` timing) — rename it to
   something that says what it is, e.g. `readCachedVariants`. It is still used by the fill path to
   report `variants` and `latencyMs`.

2. **Add a non-filling mode to the subscription route** — the same route, not a new one:

```
GET /subscription/:userId?fill=false
  → 200 { userId, source: "cache" | "miss", hit, variants, latencyMs }
```

   `fill` defaults to `true`, which is today's read-through behaviour, unchanged. With `fill=false`
   the handler reads through the index and returns what it finds: `source: "miss"`, `hit: false`,
   `variants: 0` for a user whose cache is empty. That is the **correct** answer after an eviction,
   not an error, and there is no scan fallback and no origin call. `latencyMs` remains the Redis
   round trip only. `?v=` is irrelevant in this mode and must be ignored rather than rejected.

3. **Point the two callers at it**: `services/benchmark/src/runner.ts` (the poll) and
   `scripts/verify.mjs` (the control-user check) both call
   `GET {TEST_API_URL}/subscription/:userId?fill=false`.

4. **A test must prove the probe writes nothing.** Evict a user, call the probe several times against
   the empty cache, and assert `DBSIZE` is unchanged and no key or index member for that user exists.
   Everything in `make verify` rests on this.

5. Clean up the stale references: `services/CLAUDE.md`, and the `/entitlement` wording in `prd.json`'s
   US-003 and US-009 criteria — those stories are `passes: true` and their text should not describe an
   endpoint that no longer exists. Do **not** change their `passes` flags.

## Part 2 — a second marker: the eviction finished

The chart draws one vertical dashed line, "eviction batch dispatched". Add its counterpart at the
moment the webhook's job reached a terminal state.

### Where the time comes from

Not from the poll that noticed. The webhook's `GET /jobs/:id` already returns **`finishedAt`** (ISO,
`null` while running), so the marker lands on the real instant the job ended rather than on the
1-second polling grid. For a v2 run the whole eviction takes a fraction of a second, and a marker
snapped to the poll interval would be up to a second wrong on a duration that *is* the argument.

So: carry `finishedAt` into `RunJobCounters`, and when a poll first observes a terminal `state`, emit
one lifecycle frame:

```jsonc
{ "t": "batch-completed", "runId": "...", "mode": "v2",
  "ts": 1789200003123,        // Date.parse(job.finishedAt)
  "elapsedSec": 3.124,        // fractional, 3 decimals, from the run's startedAt
  "state": "done",            // done | stopped | failed
  "processed": 1000, "removed": 1998, "incomplete": 0 }
```

Emit it **once** per run. Polling continues afterwards — the flat line after the eviction is part of
what the chart shows, so do not auto-stop the run.

**Make the dispatch marker fractional too.** It currently rounds `elapsedSec` to whole seconds. If
completion is fractional and dispatch is rounded, a fast v2 run can draw "completed" *before*
"dispatched" (dispatch 5.6 → 6, completion 5.9). Both markers use the same fractional convention.
Sample frames keep their existing rounded `elapsedSec`; only the two markers change.

### Drawing it

Beside the existing batch marker, in the same style — dashed, full plot height — with:

- **Colour by terminal state, not always green.** `done` → green; `stopped` → amber; `failed` → red.
  Add the colour constants next to `C_BATCH`. The user-visible promise is "green means the eviction
  completed successfully", and a green line over a job that was stopped halfway would be a lie the
  chart tells on the demo's behalf.
- **Label text by state**: `done` → `eviction completed (1,000 users, 1,998 keys)`;
  `stopped` → `eviction stopped after 37 of 1,000`; `failed` → `eviction failed — 12 entities incomplete`.
- **Label collision.** On a v2 run the two markers are a fraction of a second apart and their labels
  will overlap. When the two x positions are closer than the width of the first label, draw the second
  label on a second row (`padT + 16`) instead of the first. Right-align it if it would run off the
  plot.
- **A legend entry** for both markers, so a reader who hasn't been told knows what the lines are.

### The rest of the wiring

- `HistoryFrame` carries the completion (`completedAt`, `completionState`, and the counters), and
  `ActiveRun` holds it, so a browser that connects or reloads mid-run redraws both markers rather than
  only the dispatch line.
- The UI state (`state.run`) gains `completedSec` and `completionState`, set from either the
  `batch-completed` frame or the history frame, and cleared on `run-started`.
- `docs/API.md` gains the `batch-completed` frame in the WebSocket frame list; `README.md`'s "what
  each run should look like" gets one sentence: on v2 the two lines are almost on top of each other,
  and on v1 you will normally see the amber *stopped* line, because a thousand keyspace scans is not
  something you wait out.

That last point is worth getting right rather than treating as a caveat. **The v1 marker will almost
always say "stopped", and that is the most eloquent thing on the chart**: the fast run has a
completion line, the slow one has the line you drew when you gave up.

## Self-check

```bash
grep -rn "entitlement" --include=*.ts --include=*.mjs --include=*.md --include=*.json services packages scripts docs prd.json
# only historical mentions in tasks/ and progress.txt may remain
make typecheck && make test
make up

curl -s "localhost:3001/subscription/u_0000001?fill=false" | jq   # source:"cache", latencyMs, no origin call
curl -s "localhost:3001/subscription/u_9999999?fill=false" | jq   # source:"miss", hit:false, variants:0, 200
docker compose exec -T redis redis-cli dbsize                      # unchanged by the two calls above

# run v2 from the UI, then check the captured frames carry the marker:
node scripts/capture-run.mjs v2 20 /tmp/run-v2.json
jq '[.[] | select(.t=="batch-completed")]' /tmp/run-v2.json        # exactly one, state:"done", fractional elapsedSec
jq '[.[] | select(.t=="batch-dispatched")][0].elapsedSec' /tmp/run-v2.json   # fractional too

make verify                                                        # still exits 0
```

Then open `localhost:3000`, run v2, and look at it. Two lines a fraction of a second apart with
legible, non-overlapping labels is the acceptance criterion no `jq` expression can check. Run v1,
press Stop after twenty seconds, and confirm the amber line and its "stopped after N of 1,000" label.
