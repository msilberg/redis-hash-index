# US-004 — webhook, both invalidation paths

## The comparison this story exists to make fair

Two endpoints, identical inputs, identical fixture, one Redis. The only difference is how each
finds the keys belonging to a user. If you make v1 artificially bad the demo is worthless; if you
make it artificially good it doesn't reproduce. Write the legacy path the way a competent engineer
would have written it in 2019 — because that is exactly how it got written.

## `POST /v1/invalidate` — the legacy path

Per user, one scan then delete the matches:

```
KEYS *::<userId>::*
```

The `::` on both sides is required. `*<userId>*` would also match the index key — whose name ends
at the id — and would match those characters anywhere else, including inside a `params` tail. Use
`UNLINK` for the deletes so the only variable under test is *discovery*.

## `POST /v2/invalidate` — the index path

Delegate to `packages/cache` `invalidateEntities`. No new logic here.

## Both endpoints return 202 immediately

A 1,000-user v1 batch is roughly 35 minutes at 2M keys and about 3 hours at 10M. A synchronous
response would hang the request, block the browser and make the demo unusable. Return
`{jobId, mode, total}` at once and run the work in the background.

## Job model

An in-memory `Map<jobId, Job>` is the right amount of machinery for a demo. Persisting it would be
gold-plating.

```ts
type Job = { jobId: string; mode: 'v1' | 'v2'; state: 'running'|'stopped'|'done'|'failed';
             total: number; processed: number; removed: number;
             startedAt: string; finishedAt: string | null; error?: string };
```

`POST /jobs/:id/stop` sets a flag the worker loop checks **between users**, never mid-user. Because
v2 deletes values before references, a user interrupted partway is simply re-invalidatable — do not
add compensation logic.

## Integration test

Seed roughly 200 keys across ~80 users, split them into two disjoint groups, run v1 on one and v2
on the other, poll each job to `done`, then assert:

- every cache key for both groups is gone;
- every index key for the v2 group is gone;
- an unrelated user's keys are untouched (this catches an over-broad `KEYS` pattern);
- stopping a running job leaves `state: 'stopped'` and a `processed` below `total`.

## Self-check

```bash
make up && make test
curl -s -XPOST localhost:3002/v1/invalidate -H 'content-type: application/json' \
  -d '{"userIds":["u_0000001"]}'          # 202 with a jobId, returns instantly
curl -s localhost:3002/jobs/<jobId> | jq
make typecheck
```
