# US-010 — cache strategies, the `@Cache` adapter, and a lazily-filled fixture

## What this story is

The repo currently exposes one class, `EntityIndex`, and every caller talks to Redis around it.
This story turns that into the shape the design actually came from: a small **strategy hierarchy**
behind a **`@Cache` decorator**, so a service caches a method by annotating it and never names a key.

Four things, in this order:

1. `DefaultCacheStrategy` — owns the Redis client, `get` and `set`.
2. `EntityIndexCacheStrategy extends DefaultCacheStrategy` — the renamed `EntityIndex`, whose `set`
   also registers the key in the entity index.
3. `@Cache(cacheKey, ttl, strategy)` — the pre-hook adapter, plus the `CacheKey`, `TTL` and
   `CacheStrategy` enums it takes.
4. A mock `BillingProvider` and a **lazy** seeding path, so `make up` exercises the decorator end to
   end instead of only the bulk writer.

## 1. `DefaultCacheStrategy`

`packages/cache/src/strategies/default.ts`, exported from the package index.

```ts
export class DefaultCacheStrategy {
  protected readonly redis: RedisClient;          // shared with every subclass
  constructor(redis: RedisClient, options?: DefaultCacheStrategyOptions) { … }

  async get(key: string): Promise<string | null>;
  async set(key: string, value: string, ttlSeconds: number): Promise<void>;
}
```

- `redis` is `protected readonly`, so a subclass uses the same connection rather than opening or
  being handed a second one. That is the point of the base class.
- `get` is a plain `GET`. `set` is `SET key value EX ttl`.
- `set` validates the TTL with the existing `assertValidTtl` **before** issuing any command. A
  rejected call writes nothing.
- The class knows nothing about indexes, categories or entity IDs. Keep it that way — a strategy
  that has to be told about its subclass is not a base class.

## 2. Rename `EntityIndex` → `EntityIndexCacheStrategy`, and make it a real subclass

A repo-wide rename with **no backwards-compatibility alias**: `packages/cache`, `webhook`,
`test-api`, `benchmark`, every test, `docs/REDIS-SCHEMA.md`, `tasks/US-002.md` and `prd.json`'s
US-002 text. Grep for `EntityIndex` afterwards; the only matches should be the new name.

```ts
export class EntityIndexCacheStrategy extends DefaultCacheStrategy {
  override async set(key: string, value: string, ttlSeconds: number): Promise<void> { … }
  // parse, indexKeyFor, register, registerMany, invalidateEntities, prune — unchanged behaviour
}
```

### The `set` override — read this part before writing it

The intent is the pseudo-code shape: **the child's `set` writes the value and registers it.**

```ts
public async set() { await super.set(); await register(); }
```

Implemented **literally**, that is two separate round trips, which re-opens the write/registration
window PR #5 deliberately closed: an invalidation landing between the `SET` and the `SADD` never
sees the value, and the value then survives to its TTL with nothing pointing at it. So implement the
shape, not the two round trips:

```ts
override async set(key: string, value: string, ttlSeconds: number): Promise<void> {
  const parsed = this.parse(key);
  if (parsed === null) {
    await super.set(key, value, ttlSeconds);        // not an indexed category: a plain SET
    return;
  }
  await this.registerMany([{ cacheKey: key, value, ttlSeconds }]);   // SET EX + SADD in one MULTI
}
```

`registerMany` already queues `SET ... EX`, `SADD`, `EXPIRE NX` and `EXPIRE GT` in a single `MULTI`.
So the override still *is* "write the value, then register it" — it just does both atomically, and
falls back to the parent for a key this strategy does not own. A comment above the override must say
why it does not call `super.set()` on the indexed path, because that looks like an oversight and is
not one.

`get` is inherited unchanged: reading through the index is `test-api`'s job (`SMEMBERS` + `MGET`), a
different operation from fetching one cache key by name.

## 3. The enums and the `@Cache` adapter

`packages/cache/src/cache-decorator.ts`, exported from the package index.

```ts
export enum CacheKey { ACTIVE_SUBSCRIPTION = "activeSubscription", PLAN_CONFIG = "planConfig" }
export enum TTL { SHORT = 300, MEDIUM = 3600, LONG = 86_400 }
export enum CacheStrategy { DEFAULT = "DEFAULT", ENTITY_INDEX_CACHE = "ENTITY_INDEX_CACHE" }
```

`CacheKey`'s values are the **category** segment of the key schema and must match
`docs/REDIS-SCHEMA.md`. `TTL.MEDIUM` is 3600, the value the fixture already uses.

### Wiring, because a decorator cannot be handed a Redis connection

Decorators evaluate when the class is defined, long before a connection exists. So the package needs
a tiny registry, configured once at service bootstrap and resolved **at call time**:

```ts
configureCache({ redis, service, tenant, categories });   // once, in each service's index.ts
```

- The registry constructs one `DefaultCacheStrategy` and one `EntityIndexCacheStrategy` over the
  supplied client and returns them by `CacheStrategy` value.
- A decorated method called before `configureCache` throws a clear error naming the missing setup.
  It must not silently bypass the cache.

### `@Cache(cacheKey, ttl, strategy)`

A **standard TypeScript 5 decorator** — TS 5.6 and target ES2022 are already configured. Do **not**
enable `experimentalDecorators` and do **not** add `reflect-metadata`.

```ts
class SubscriptionService {
  @Cache(CacheKey.ACTIVE_SUBSCRIPTION, TTL.MEDIUM, CacheStrategy.ENTITY_INDEX_CACHE)
  async getActiveSubscription(userId: string, params: RequestParams = {}): Promise<Subscription> {
    return await BillingProvider.getActiveSubscription(userId);
  }
}
```

Behaviour, in order:

1. Build the cache key: `service::tenant::<cacheKey>::<entityId>::<params>`, where `entityId` is the
   **first argument** and `params` is a **canonical** `JSON.stringify` over sorted keys, so
   `{a:1,b:2}` and `{b:2,a:1}` produce one key. A key the decorator builds must round-trip through
   `parse()` unchanged — assert that in a test. A first argument that fails the segment character
   class throws rather than being escaped.
2. `strategy.get(key)`. On a hit, `JSON.parse` and return without calling the method.
3. On a miss, call the original method, then `strategy.set(key, JSON.stringify(result), ttl)` and
   return the result.
4. **Single-flight**: concurrent misses for the same key in the same process collapse to one call of
   the underlying method. An in-process `Map<string, Promise<T>>` cleared in a `finally` is enough.
5. **A throw is never cached.** If the method rejects, the rejection propagates and nothing is
   written. An `undefined` return is likewise not cached. Only an explicit
   `{ cacheNegative: true, negativeTtl }` option caches a `null` result, and it defaults to off.

Rule 5 is the whole reason this story is worth doing carefully: the original version of this
decorator wrapped the provider call in a `try/catch` that returned `undefined`, which the cache then
stored, turning a five-second provider blip into a cached "this user has no subscription" for the
rest of the TTL. The mock provider must make that testable, and a test must prove it.

## 4. The mock provider and lazy seeding

### `BillingProvider` — `services/benchmark/src/billing-provider.ts`

A stand-in for the third-party billing API. Deterministic: it must produce, for a given `userId`,
**exactly the record the bulk fixture generator produces for that user** (reuse `fixture.ts` and its
seeded PRNG), so a lazily filled user and a bulk-seeded user are byte-identical in Redis.

- `ORIGIN_LATENCY_MS` (default 0 in bulk mode, 150 when a latency is wanted; range 0..60000) — an
  awaited delay before answering, so the fill is observably slower than a hit.
- `ORIGIN_FAIL_USER` — an optional user ID for which it always throws, so rule 5 above is
  demonstrable with `curl` and not only in a unit test.
- It must **not** touch Redis. It is the origin.

### Seeding modes — and the constraint that shapes this

`make up` must keep seeding 2,000,000 records in about a minute. That is only possible because the
bulk writer pipelines ~20,000 commands per round trip. A decorated, lazily-loaded fill is one
`GET`, one origin call and one `MULTI` **per record**; at two million records that is hours. Both
paths must therefore exist, and the default must stay fast.

`SEED_MODE`, default `bulk`:

- `bulk` — today's behaviour: `generateUsers` → `registerMany` in pipelined batches. Unchanged.
- `lazy` — every record is filled by calling the decorated `getActiveSubscription`, with bounded
  concurrency (`LAZY_CONCURRENCY`, default 16). Intended for small fixtures; the seeder must refuse
  `lazy` above `LAZY_MAX_KEYS` (default 50,000) with an error that names the flag, rather than
  appearing to hang.

**And in both modes**, after seeding completes, the seeder lazily fills `LAZY_WARM_USERS`
(default 1,000) users **through the decorator** — reported as its own progress phase, `lazy-warm`.
So `make up` always exercises the `@Cache` path end to end, at a cost of about a second, while the
bulk of the fixture is still written the fast way. The lazy-warm users are the same
`userIdFor(0..999)` batch the eviction run targets, so the demo's default run evicts records that
were filled through the decorator.

This is a deliberate deviation from "the seeder fills everything lazily": that reading would make
`make up` take hours at the default fixture size. If the intent was the literal one, flip the
default to `SEED_MODE=lazy` and drop `SEED_KEYS` to 50,000 — one line each, and the story is
otherwise unchanged.

## Self-check

```bash
grep -rn "\bEntityIndex\b" --include=*.ts --include=*.md --include=*.json . | grep -v node_modules   # no matches
grep -rn "experimentalDecorators\|reflect-metadata" . --include=*.json --include=*.ts                # no matches
make typecheck && make test

make up                                   # still ~1 minute at SEED_KEYS=2000000
docker compose logs benchmark | grep lazy-warm     # the lazy phase ran

# the decorator path, twice: miss then hit
docker compose exec -T benchmark node -e '…'       # or the US-009 route once it exists

# a failing origin caches nothing
ORIGIN_FAIL_USER=u_0000002 docker compose up -d benchmark
docker compose exec -T redis redis-cli --scan --pattern '*u_0000002*' | head    # no output

SEED_MODE=lazy SEED_KEYS=50000 make reset seed      # completes; DBSIZE matches bulk for the same seed
SEED_MODE=lazy SEED_KEYS=2000000 make seed          # refuses, naming LAZY_MAX_KEYS
make verify                                         # still exits 0
```

The last check that matters is not a command: seed the same `SEED_VALUE` in `bulk` and in `lazy` and
compare `DBSIZE` and a sampled key's value and TTL. If the two paths disagree, the decorator is
building a different key than the fixture generator, and every claim in the write-up about "the same
records, two ways" is wrong.
