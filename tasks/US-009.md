# US-009 — the read path: a read-through cache in front of a slow origin

## Why this story exists

Every story so far treats the cache as something that is *already full*. The seeder writes the
fixture, the webhook deletes it, `test-api` reads it. Nothing in this repo has ever performed a
**cache fill**, which means the repo cannot demonstrate the one failure mode the write-up spends
the most words on: a fill that begins before an invalidation and lands after it.

It also means the interesting production shape is missing. In the system this demo is modelled on,
nobody called Redis directly. A shared decorator wrapped the method that talked to the billing
provider, and the caching was invisible at the call site:

```ts
class SubscriptionController {
  @Cache(CacheKey.ACTIVE_SUBSCRIPTION, TTL.MEDIUM, CacheStrategy.DEFAULT)
  public async getActiveSubscription(userId: string): Promise<ActiveSubscription | undefined> {
    return await BillingProvider.getActiveSubscription(userId);
  }
}
```

That is what makes the composite key so easy to arrive at and so hard to delete from: the key is
built by the framework from the method's arguments, and no human ever looks at it until the day
something hands them one user ID and says "invalidate this".

Build that. It is the missing half of the demo.

## What to build

### 1. `packages/cache` — a read-through wrapper and a decorator

A new module in the shared package (`packages/cache/src/read-through.ts`, re-exported from the
package index). Two exports over one implementation, exactly as `register` / `registerMany`:

```ts
readThrough<T>(coords: ReadCoords, load: () => Promise<T>): Promise<ReadResult<T>>
```

and a **method decorator** built on it, so a service can write the shape above. TypeScript 5.6 and
target ES2022 are already configured, so use **standard decorators** — do NOT enable
`experimentalDecorators`, and do NOT add `reflect-metadata`.

```ts
class SubscriptionReader {
  @Cached({ category: CATEGORY, ttlSeconds: 3600 })
  async getActiveSubscription(userId: string, params: RequestParams): Promise<Subscription | null> { … }
}
```

Behaviour, in order:

1. Build the cache key from `service`, `tenant`, `category`, `entityId` and a **canonical**
   serialisation of the parameters — `JSON.stringify` over sorted keys, so `{a:1,b:2}` and
   `{b:2,a:1}` are the same key. Reuse `parse`'s delimiter and segment rules; a key this builds must
   round-trip through `parse` unchanged. Assert that in a test.
2. `GET` it. On a hit, return `{ value, source: "cache" }` without touching the origin.
3. On a miss, call the loader, then write **through `registerMany([{ cacheKey, value, ttlSeconds }])`**
   so the `SET ... EX` and the `SADD` are in the same transaction. Return `{ value, source: "origin" }`.
4. **Single-flight.** Concurrent misses for the same cache key in the same process collapse to one
   loader call. An in-process `Map<string, Promise<T>>` cleared in a `finally` is enough. Without
   this, a slow origin plus a warm-up loop is a self-inflicted thundering herd — the exact thing
   the write-up criticises `FLUSHALL` for causing.

### 2. The rule that this story exists to get right

**An origin failure must never be cached.** If the loader throws, the wrapper propagates the error
and writes nothing to Redis. A transient provider blip must not become a cached "this user has no
subscription" for the rest of the TTL.

An *authoritative* negative answer is different: if the origin successfully returns "no such
subscription", that is a real result and may be cached, but only under an explicit
`cacheNegative: true` option that defaults to **false**, and with its own shorter TTL
(`negativeTtlSeconds`). Distinguishing "the origin said no" from "the origin did not answer" is the
whole point; a `catch` that returns `undefined` collapses the two and is the bug this story fixes.

### 3. `test-api` — a fake origin and a read-through route

A `BillingOrigin` module: deterministic (same PRNG conventions as US-005), with

- `ORIGIN_LATENCY_MS` (default 150, range 0..60000) — a `setTimeout` delay before answering,
- `ORIGIN_FAIL_USER` — an optional user ID for which the origin always throws, so the
  never-cache-an-error rule is demonstrable with `curl`, not only in tests.

New route, alongside the existing `GET /entitlement/:userId`, which does **not** change:

```
GET /subscription/:userId?includeAddons=true
  → 200 { userId, source: "cache" | "origin", variants, latencyMs, subscription }
  → 502 { error } when the origin throws — and nothing was written to Redis
```

`latencyMs` continues to mean the Redis round trip only; report origin time separately as
`originMs` when `source` is `"origin"`. Validate `:userId` against `^u_\d{7}$` → 400. The service
still must never call `KEYS` or `SCAN`.

### 4. The interleaving test — the reason this story is worth doing

An integration test against real Redis (same harness as `packages/cache`'s tests) that reproduces
the race the write-up describes, and **asserts the documented outcome rather than pretending it is
fixed**:

- **Fill starts, invalidation lands mid-flight.** Begin a read-through fill for a user with a slow
  origin. Before it resolves, invalidate that user. Assert the invalidation removed what existed at
  the time, the fill then writes its value and its reference, and the value **survives to its TTL** —
  bounded staleness, exactly as documented. Assert also that the index reference and the value agree
  (no orphan value, no dangling reference), because that is what `registerMany` buys.
- **Invalidation lands after the fill completes.** Assert both value and reference are gone.
- **Origin error is not cached.** Force a failure, assert the call rejects, assert no key and no
  index member were created, and assert a second call still reaches the origin.
- **Single-flight.** Fifty concurrent misses for one key produce exactly one loader call.
- **Key round-trip.** A key built by the wrapper parses back to the same coordinates.

## Documentation

- `docs/API.md` — the new route, its response shape, and the 502-writes-nothing rule.
- `docs/ARCHITECTURE.md` — a "read path" section: what the decorator hides, why the key is easy to
  build and hard to delete from, and precisely what the interleaving test demonstrates (bounded
  staleness, not atomicity). State that closing the race properly needs generation numbers and that
  this demo deliberately does not.
- `README.md` — one line under the caveats: the demo now fills as well as evicts, and the origin is
  fake and deterministic.

## Out of scope

The benchmark UI, the run driver, and the seeder. The seeder keeps writing the fixture directly
through `registerMany`; it does not go through the read-through wrapper.

## Self-check

```bash
make typecheck && make test
make up
curl -s "localhost:3001/subscription/u_0000001?includeAddons=true" | jq   # source:"origin", originMs present
curl -s "localhost:3001/subscription/u_0000001?includeAddons=true" | jq   # source:"cache"
curl -s "localhost:3001/subscription/u_0000001?includeAddons=true"  | jq -r .source
# force the failure user, then prove nothing was cached:
ORIGIN_FAIL_USER=u_0000002 docker compose up -d test-api
curl -s -o /dev/null -w '%{http_code}\n' localhost:3001/subscription/u_0000002   # 502
docker compose exec -T redis redis-cli --scan --pattern '*u_0000002*' | head     # no output
grep -rn "KEYS\|scan(" services/test-api/src                                     # no matches
grep -rn "experimentalDecorators\|reflect-metadata" . --include=*.json --include=*.ts  # no matches
make verify                                                                      # still exits 0
```

Then re-read `docs/ARCHITECTURE.md` and check that what it claims the interleaving test proves is
what the test actually asserts.
